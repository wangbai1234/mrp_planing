## 二、业务对象与唯一口径

1. **来源月**＝经营计划需求归属月；**生产日**＝实际整机排产日期；**月汇总列**＝生产日所属自然月。三者必须明确区分，不能为了合行改变 v5 的“按来源月拆业务周并整体前移一业务周”公式。
2. 一个业务版本仍是一个 `batchId`，一次有效计算仍以 `activeRunId` 为准。整机日事实、末级需求、物料日备料、确认指纹和最终发布属于同一版本链；切页不复制事实、不创建第二套发布。
3. “物料缺料”是工作台名称，首页数值命名为**末级净需求／库存风险**。`STOP` 可使机头、PCBA 成为末级，不一律叫原材料；未接采购在途、承诺到货、预计/实际收货和交期覆盖时，不得生成“真实到料缺口”或以 0 冒充。
4. 产能值是**冻结配置**，不是系统自动算出的可生产量。负荷来自整机日计划有效值，单位必须是台；产能比较以工厂＋生产日为粒度。超限量＝`MAX(0,负荷－日产能)`；周/月负荷仅作为日事实求和，不把“日产能 10”简单加成一个可承诺周能力。
5. 当前超产能沿用既有“预警明细＋绑定当前结果的人工确认”发布规则。若希望极端超限自动阻断发布，应单独做业务裁决，不在此次界面优化中暗改门禁。

### 3.1 默认一行一个“工厂＋整机”

- 只在**表现层和服务端分页查询**合并 `MACHINE_OUTPUT` 行；日单元格将同一工厂、整机、日期的各来源月有效量精确相加。不同工厂不能合并；同一工厂跨来源月可合并。保留现有明细事实及原始来源月键。
- 日／周／月三种视图共享这一行粒度。日格点击后先看日期来源月拆分；再点击某一事实才能调日。若某日涉及两个来源月，不允许对合并数直接调日，因为会丢失来源归属与审计。
- “来源月”从固定列移至明细和可选筛选；在详情显示该月经营计划量、整机良品库存分配、根净台数、排产日数量与调日记录。六个月不是六条重复业务记录，只是六个来源的不同分配。
- 合计列应写清“本次筛选范围内的整机总量”，并与日期轴展示范围一致。若只展示 28 天，不能把 84 天行总量标成当前视窗合计；可以显示“全计划合计”并给出日期范围。负荷行右侧合计应隐藏或明示“期间累计负荷”，绝不能当作日产能。
- 服务端先按 `runId＋工厂＋整机` 做 `COUNT/DISTINCT`、分页，再取该页所有来源月的日事实与有效 override 后聚合。筛选、导出、详情必须用同一数据口径；不能只把前端当前页六行相加，因为会破坏服务端分页。

### 3.2 负荷和日产能

- 固定行命名“**已排整机负荷 / 冻结日产能（台）**”；左侧必须可见工厂名，固定行点击显示同工厂同日所有整机的贡献和来源月，服务端分页，不受整机搜索词限制。
- 日格现分行显示“已排 11,255 台 / 日产能 10 台 / 超出 11,245 台”；严重超限仍应提示“请核对排产输入或产能配置”，而不是默认为系统算错。用户可以下钻到贡献整机；冻结日历版本在版本信息中显示，对应配置维护页仍需清晰回跳。
- 对用户当前所见数值，先取得页面实际 batchId、activeRunId、工厂和日期，再重放该 batch 的 `rolling-grid` 与同日 `rolling-details`，按 `factory_code,schedule_date,root_material_code,source_month` 汇总 `MACHINE_OUTPUT` 有效值，核对 11,255 是否逐项守恒；再核对该 batch 冻结生产日历是否为 10 台。历史 #60 只是仓库中数值相同的证据，不等于用户当前批次；若当前库不可得，保持“当前数值组成未核实”结论。

### 3.3 “版本详情”和生产日历检查

- 页头“版本详情”改“版本信息”，只展示版本号、来源批次/修订、工厂范围、run、规则版本、输入版本与 checksum、创建/发布时间、双方确认快照；用约 640–760px 抽屉或小对话框。没有批次时不显示。历史版本只读。
- “生产日历检查”作为排产页筛选工具栏右侧的**独立入口**；有缺失才显示醒目的异常计数。检查结果采用紧凑抽屉：顶部标题＋状态＋[维护生产日历][维护业务周][重新检查]，下方仅在异常时列具体缺失日期/配置，正常时一行成功空态即可。按钮不再散落在 86% 宽抽屉底部。
- “执行与锁定”放在排产页二级标签或行操作中；无相关结果时不占页头。生产日历输入已随批次冻结，维护主数据后须新建草稿或修订版，不能假装“重新检查”会替换旧批次冻结值。

### 4.1 首页只保留要做的事

- 移除常驻的“本页展示末级净需求……”长提示，改为标题旁“数据口径”帮助入口，写清库存净需求的计算边界。不要在每次浏览时重复展示采购在途限制。导出报表表头及详情仍须标注“未计在途/承诺到货”。
- 移除独立的“物料策略提示与默认下钻确认”页外按钮。将其并入“**待处理**”抽屉/标签，显示具体待确认条数、责任人和确认动作；未处理时继续阻断物料确认和发布。库存风险、决策、分配、反馈也进入同一待办概览，再按类别下钻。
- 移除“同一版本 · 整机确认……正式发布……”整段重复状态栏。页头只显示 `#批次＋阶段`，下一步动作由状态决定；完整确认人与时间、run、输入版本放到版本信息。已发布版展示发布时的确认快照，绝不再显示“待复核”。
- 默认主表为“按物料汇总”，建议一行一个 `批次/run＋工厂＋末级物料`；跨来源月合并展示**一次**总净需求和来源月个数，按月/整机在下钻中看。若同码对应不同终点类型或供应方式，应拆分子行/分别标识，不能混淆处理动作。多仓扣库时，仓库列显示“多仓”并下钻各良品库存池的分配、安全库存和风险；**不能把同一物料净需求复制到每个仓库行**，也不能跨工厂加库存。当前 SQL 只提供按物料聚合的净需求，尚缺库存池、风险和状态联查，须由后端补。
- 默认列保留工厂/仓库范围、物料编码/名称/单位、末级净需求、风险/待办状态、受影响整机数与操作。毛需求、逐层已分配、安全库存、供应方式、STOP 原因、BOM 路径、操作者放在详情，按实际处理需要出现。若默认表展示“可用库存”，必须说明是冻结总池还是某一仓实际分配量，不能把全池库存重复显示在每个来源月行。
- 若用户筛选某个整机或来源月，列名改“**筛选范围净需求**”，风险和库存池总量仍按**完整版本**判定，不能在筛选结果上重新扣同一份库存。汇总结果的服务端分页、排序、筛选和导出需同口径。
- 暂保留“日备料”和“计算追溯”作为次级工作区，或合并在物料详情；不要让七个同级标签长期挤占表格首屏。日备料从排产页跳入时应带同一工厂、整机、日期和来源月筛选。

### 4.2 空态和状态动作

| 阶段 | 缺料页显示 | 允许动作 |
| --- | --- | --- |
| 草稿/整机未生成 | “整机排产尚未生成” | 查看排产准备，不显示空的“缺料 0” |
| `SCHEDULE_READY` 且未确认 | “等待排产员确认整机日计划” | 返回排产；物控不能提前确认物料 |
| 整机已确认 | “待物控开始物料分析” | 物控点击“开始物料分析”，提交异步任务并轮询 |
| 分析中/失败 | 进度或明确错误 | 幂等查询、按既有规则重试，不能将旧结果当成当前结果 |
| `MATERIAL_REVIEW` | 物料清单、风险和待办计数 | 处理异常、分配、反馈、确认 |
| `MATERIAL_RECALC_REQUIRED` | “库存分配变更，结果待重算” | 重算前保留/显式处理人工决策，不静默清空 |
| 双岗已确认/`READY` | “待发布” | 授权人按既有门禁发布 |
| `PUBLISHED` | 只读的正式版本和发布时确认快照 | 查看追溯；修改需修订 |

## 五、双工作台交接闭环

```text
冻结输入并预检整机根层
  → 生成整机根净需求和 MACHINE_OUTPUT 日事实（SCHEDULE_READY）
  → 排产员核对日历/产能、调日、确认当前排产指纹
  → 物控在缺料页点击“开始物料分析”（清晰的人工交接点）
  → 同一 run 从已净额的整机根需求展开 BOM、逐层扣冻结良品库存
  → 生成末级净需求、日备料和异常（MATERIAL_REVIEW）
  → 物控处理异常、默认下钻、分配、风险和排产反馈
  → 物控确认当前物料指纹（READY）
  → 发布责任人核对双确认及原有门禁，生成独立发布版本
  → 执行/锁定；未来变更走修订，不改写历史。
```

本次建议保留现有**物控显式启动**交接：它明确两岗责任，且不改异步任务时序。排产页确认成功后立即显示“排产已确认，等待物控开始分析”，并有“查看物料缺料”跳转；缺料页给唯一主按钮。后续若业务认为无需手动交接，可另评估自动入队，但不能在只做界面精简时悄悄更改任务触发规则。

物控提出缺料反馈时，记录工厂、整机、来源月、涉及生产日/物料、影响数量、建议日期、原因和责任人；排产员决定接受调整或给出处理理由。整机调日后，同 run 的关联备料按当前服务原子联动；物料确认自动失效，物控重新分析/复核。人工分配变更使物料结果失效并重算；BOM/冻结输入变化沿既有 STALE/新批次规则处理。任何过期指纹提交返回冲突提示。**发布仍要求两个当前指纹确认、反馈关闭、阻断问题和待分配清零、日历与守恒检查通过；产能预警按现有绑定指纹确认。**

## 六、最小实现落点与明确缺陷

## 七、验收标准与交付顺序

1. **正确性先行。** 同工厂同整机六个来源月默认只占一行；任一日的合并量＝明细六个月之和；日格能拆到精确来源月事实并只调整所选事实；不同工厂不会串行；日／周／实际自然月总量守恒，导出一致。
2. **产能可解释。** 每个工厂日期负荷＝所有有效 `MACHINE_OUTPUT` 整机事实和，且点击可分页追溯；冻结日产能能追到日历版本。历史 #60 的 11,255/10 若无数据库明细，不声称已经证实其业务合理性。
3. **交接可见。** 未确认整机不会生成 v5 末级结果；确认后缺料页显示待物控启动；分析中有任务进度；成功后显示末级需求；调日/分配变更后旧确认不可继续发布；反馈来回留审计。
4. **发布状态真实。** 发布前双确认与门禁正常；发布后的两页读取同一发布版本和发布时确认快照，不显示“已发布／待复核”的伪冲突；旧历史无证据则显示不可追溯。
5. **缺料口径准确。** 默认按工厂＋物料服务端分页，库存池在详情中分列；同一物料跨仓库只展示一次总净需求，库存不会因筛选/跨来源月重复扣；库存风险与零库存/缺记录明确区分；在途和交期缺口不显示为零。
6. **交付门禁。** 先改原型和上述 P0，再做 P1/P2。每次代码改动后执行项目规定的编译、单测、启动真实 API/Worker、5180 前端与浏览器/curl 验证；独立复核 PASS 后才从 REVIEW 转 DONE。当前 8180 健康检查 Oracle 探针 503 和 v5 全链路 UAT 未完成，不用静态页 200 代替验收。

**建议分两次合入：**第一批修正明细串月、发布状态和列表/产能解释；第二批完成一行整机、缺料按物料聚合及库存池下钻、页面精简。这样不触碰 v5 排产公式、BOM 扣库公式和原有发布条件。
