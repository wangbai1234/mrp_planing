# MRP 执行铁律

> 从 heart 项目工程实践提炼，适用于 MRP 项目所有阶段。违反必须立即停下修复。

---

## 1. 验证铁律

### 1.1 三层验证（缺一不可）

| 层 | 内容 | 不可省略 |
|---|---|---|
| **编译** | `./mvnw compile` / `npm run build` | 每次改动后 |
| **单元测试** | `./mvnw test` | 每次改动后 |
| **集成联调** | 实际 API 调用 + 前端页面验证 | 每个 Prompt 完成后 |

**禁止只验证编译和单元测试就报告完成。必须实际启动服务，用真实请求验证 API 返回正确数据，用浏览器验证页面能正常加载和交互。**

### 1.2 集成验证分档

| 档 | 类型 | 处置 |
|---|---|---|
| **A** | 功能性错误（页面加载失败、API 返回错误、数据不正确） | 立即停下，必须修复 |
| **B** | 新引入的 lint/类型错误 | 等同档 A，禁止静默 |
| **C** | 既有债务 | 不阻塞，记录到 issue-log |
| **D** | 领域约定与 lint 规则冲突 | 局部禁用 + 注释理由 |

## 2. 原型驱动铁律

### 2.1 原型是 UI 布局和样式参考

- **原型提供布局、颜色、组件结构的参考**，不是让你直接复刻代码
- 原型中的交互逻辑和数据必须用真实 API 调用替换
- 原型中的硬编码数据必须替换为从后端加载的动态数据
- 使用项目指定的技术栈（Element Plus、fetch API），不要自己写 CSS 代替组件库
- 原型的 CSS 变量和类名可以作为样式参考，但组件实现必须用 Vue 3 + Element Plus

**禁止：把原型的 vanilla JS 直接翻译成 Vue 语法而不连接 API。原型是设计稿，不是代码模板。**

### 2.2 原型对照清单

每个页面实现前必须对照原型确认：
- [ ] 侧边栏结构和颜色
- [ ] 顶部栏内容（面包屑、同步状态）
- [ ] 页面头部（标题、副标题、操作按钮）
- [ ] 筛选/工具栏
- [ ] 数据表格列定义和样式
- [ ] 弹窗/抽屉结构
- [ ] 空状态和加载状态
- [ ] 图例和状态标签

## 3. Spec 先行铁律

### 3.1 读 → 计划 → 实现 → 测试 → 验证

```
读 Spec → 读原型 → 计划改动 → 实现 → 单元测试 → 集成验证 → 报告
```

**禁止跳过任何步骤。特别是"集成验证"——必须实际运行并确认结果。**

### 3.2 每个任务必须

1. 引用具体的 spec section 或原型行号
2. 列出将修改的文件
3. 写测试验证
4. 实际运行验证
5. 在报告中记录真实命令和输出

---

## 4. 前端铁律

### 4.1 前端不是"编译通过就行"

- `npm run build` 只证明 TypeScript 编译通过
- 必须实际启动服务，用浏览器访问每个页面
- 必须验证 API 调用返回 200 且数据正确
- 必须验证空数据时有友好提示，不是白屏或报错

### 4.2 API 联调检查

每个 API 端点必须验证：
- [ ] 前端发送了正确的 Authorization header
- [ ] 后端返回了正确的数据结构
- [ ] 前端正确处理了空数据（data=[] 或 data=null）
- [ ] 前端正确处理了错误（401/403/500）
- [ ] 加载状态和错误状态有 UI 反馈

### 4.3 UI 文案规范

- 禁止在面向用户的 UI 中使用 emoji
- 需要强调时用字重/颜色/排版，不用 emoji
- 按钮必须有文字，不能只有图标
- 状态不能只靠颜色区分，必须有文字标签

---

## 5. DB 迁移铁律

### 5.1 迁移文件不可变

- 一旦 V001 迁移被应用到任何数据库，**禁止修改其内容**
- 需要变更必须创建新的迁移文件（V002、V003...）
- 修改已应用的迁移会导致 Flyway 校验失败

### 5.2 每次改动后

- 如果修改了迁移文件，必须重建测试数据库
- 如果修改了配置，必须重启后端服务（不是热重载）

## 6. 会话管理铁律

### 6.1 每个新会话必须

1. 读 `project.md`
2. 读 `.harness/README.md`
3. 读当前任务对应的 Prompt
4. 读原型文件（如果是前端任务）
5. 检查 workflow.yaml 当前状态

### 6.2 完成后必须

1. 运行所有测试并确认通过
2. 实际启动服务验证（不是只看测试结果）
3. 写任务报告到指定路径
4. 更新 workflow.yaml 状态

---

## 7. 禁止事项

- ❌ 只验证编译和单元测试就报告"完成"
- ❌ 不读原型就开始写前端
- ❌ 修改已应用的 Flyway 迁移文件
- ❌ 在 UI 中使用 emoji
- ❌ 用 `any` 类型绕过 TypeScript 检查
- ❌ 空 catch 不记录异常
- ❌ 前端页面白屏或报错时不处理
- ❌ 不写测试就提交代码
- ❌ `except Exception:` 不 log 不 re-raise 直接 pass
- ❌ 把原型的 vanilla JS 直接翻译成 Vue 语法而不连接 API
- ❌ 用硬编码数据代替 API 调用
- ❌ 不用 Element Plus 自己写 CSS 组件
- ❌ 原型代码直接复制粘贴（原型是设计参考，不是代码模板）

## 8. 环境与配置铁律（血泪教训）

### 8.1 绝对禁止擅自修改的技术栈配置

以下配置属于项目契约，**任何情况下不得擅自修改**：

| 配置项 | 文件 | 说明 |
|--------|------|------|
| Java 版本 | `pom.xml` | `java.version`、`maven.compiler.source/target` |
| Node 版本 | `package.json` / `.nvmrc` | `engines.node` |
| Spring Boot 版本 | `pom.xml` | `spring-boot-starter-parent` |
| 框架选型 | `pom.xml` / `package.json` | 依赖列表 |

### 8.2 环境问题处理流程

当遇到编译/运行错误时：

```
1. 分析错误原因（读错误信息）
2. 判断是否为环境问题（JDK版本、Node版本等）
3. 如果是环境问题 → 停止，询问用户如何处理
4. 绝对不能擅自修改项目配置来适配本地环境
```

### 8.3 正确做法

- ✅ 询问用户："当前环境是 Java 17，项目要求 Java 21，请问如何处理？"
- ✅ 建议用户切换 JDK 版本
- ✅ 记录问题到 issue-log

### 8.4 错误做法（禁止）

- ❌ 直接修改 `pom.xml` 中的 Java 版本
- ❌ 直接修改 `package.json` 中的 Node 版本
- ❌ 降级依赖版本来适配本地环境
- ❌ 以"本地环境不支持"为由擅自修改项目配置

### 8.5 违规后果

擅自修改技术栈配置会导致：
1. CI/CD 构建失败
2. 其他开发者环境不兼容
3. 生产环境行为不一致
4. 项目契约被破坏

## 9. 提交前自检（每次改动后必须问自己）

1. 我实际运行了代码吗？（不只是 `./mvnw test`）
2. 前端页面能正常加载吗？（用浏览器验证）
3. API 调用返回了正确数据吗？（用 curl 或浏览器 Network 验证）
4. 空数据场景有处理吗？
5. 错误场景有处理吗？
6. 我修改了 Flyway 迁移吗？（如果修改了，必须重建数据库）
7. 我引入了新的依赖吗？（如果有，需要记录到 decision-log）
8. **我修改了技术栈配置吗？（如果有，必须立即停下，询问用户）**
