# MRP Phase 1 UI Design

为计划员设计每天可用的排产工具，而不是展示型 Dashboard。先证明业务规则能在界面中被看见、操作、校验和追溯，再优化视觉。

## 先读取项目事实

开始设计或实现前：

1. 读取 `../docs/MRP需求文档v3.0（Phase 1）.md` 中与当前页面相关的章节。
2. 读取 `../assets/MRP业务规则库.md` 对应规则；发生冲突时标记冲突，不自行创造规则。
3. 涉及滚动排产、人工调整、重算或版本时，必须读取 [references/planning-contract.md](references/planning-contract.md)。
4. 要交付可运行原型或检查现有原型时，必须读取 [references/prototype-acceptance.md](references/prototype-acceptance.md)。
5. 仅在需求不明确时查询 `MRP待确认问题池.md`；不得把 Phase 2 待确认项伪装成 Phase 1 已定能力。

## 确定页面的业务任务

默认核心用户是计划员肖芳（永惠）和徐燕平（APK）。一个排产页面至少要帮助他们回答：

- 当前 12 周从哪一周开始，当前周和跨月承接周在哪里？
- 每个周数量属于哪个需求月份，为什么排在这里？
- 月需求、整机库存、已出货如何得到月可排量？
- 哪些值是系统自动值，哪些已被人工调整？
- 调整后月度总量是否守恒，是否超产能，影响哪些周和版本？
- 当前绑定哪个经营计划版本、库存快照和排产版本？
- 下一步是修正差异、重算、发布还是导出？

页面若不能快速回答这些问题，不应先增加图表或装饰模块。

## 数据排版必须反映真实计算

优先使用“固定物料信息列 + 横向 12 周时间网格”，不要把周计划拆成卡片。

- 同时显示周序号、日期范围、物理月份和来源月份。
- 跨月承接周必须有文字标签，如“10 月提前量”，不能只靠颜色。
- 月份边界、当前周、已执行周、可编辑周、人工调整值要可区分。
- 数量使用等宽数字并右对齐；周列允许横向滚动，物料列保持固定。
- 选中单元格后展示计算来源、自动值、当前值、差异、修改人和时间。
- 月度合计必须把提前到上月第 4 周的数量计入其来源月份，而不是按显示位置误计。
- 任何示例值必须能从 forecast、库存、已出货和拆周公式复算；不得为了填满页面拼凑互相矛盾的数据。

## 操作流程必须真的改变业务状态

静态按钮不算原型能力。与任务相关的动作需要有可观察结果：

- “横向查看 12 周”：用横向滚动条或触控板左右滑动查看固定 12 周；“定位当前周”只把视图回到最左侧，不改变数据、版本和窗口范围。
- “编辑周数量”：保留自动值，标记人工调整，实时更新来源月份合计和差异。
- “重算”：生成新排产版本；保留人工修改值，只重算允许重算的系统值。
- “恢复自动值”：只清除指定人工覆盖并重新核验。
- “月中变更”：已执行周锁定，只把新增可排量分配到未执行周。
- “发布”：草稿变为已发布；发布后仍可修改，并留下状态与操作记录。
- “版本对比”：只读比较差异；禁止提供历史版本回滚入口。
- “导出”：允许选择已确认字段，不承诺未定义的固定模板。

任何写操作都要给出即时反馈；校验失败时要说明差多少、属于哪个来源月份、建议检查哪些周。操作顺序不得为了演示方便绕过版本、核验和锁定规则。

## 原型范围与真实性

Phase 1 主链路是：经营计划导入 → 库存快照 → CRM 已出货 → 自动排产 → 人工调整 → 发布 → 导出。

原型优先深入完成“12 周滚动排产工作台”，再补充其他页面。使用项目真实字段和示例料号；不要用采购订单、供应商风险等通用 ERP 内容稀释当前范围。BOM 和缺料核算只可作为 Phase 2 入口或待建设状态。

模拟数据必须在数学上自洽。至少覆盖：

- `MAX(0, forecast - inventory - shipped)`；
- 前三份平均、余数前置；
- 下月第一份提前到上月第 4 周；
- 人工调整导致的月度差异；
- 月中重算锁定已执行周；
- 产能超限提示；
- 产能只按周维护和校验；真实日排产表仅用于参考字段与布局，不做日能力到周能力换算；
- 重算生成新版本但人工修改不生成版本。

## 视觉、布局与图标

采用现代企业工具风格：克制、高密度、Desktop First、适合长时间使用。

- 使用中性底色、蓝色操作色、橙色警告、红色阻断、绿色完成；状态同时写文字。
- 圆角以 4–8px 为主，避免大渐变、玻璃拟态、霓虹、大 Hero 和卡片墙。
- 顶部优先显示版本、数据时间、计划状态和核心动作。
- KPI 只显示能触发计划员动作的数量，例如待平衡月份、人工调整、超产能周。
- 详情使用侧栏、抽屉或固定下方面板，避免为一个调整连续打开多层弹窗。
- 最小支持宽度 1280px；复杂网格横向滚动，不压缩到不可读。
- 功能图标统一使用同一套 16/18/20px 线性 SVG，保持相同线宽、端点和视觉重量。
- 禁止用 emoji、颜文字或彩色表情符号充当导航、按钮、状态、警告和空状态图标。
- 文字标签承担主要语义；图标只作识别增强，不能替代“已执行”“人工调整”“超产能”等业务文字。

## 实现约束

- 先检查现有技术栈和组件；当前仅需便携原型时，可交付无依赖的单文件 HTML/CSS/JS。
- 使用 CSS variables 管理颜色、间距和尺寸，数据与渲染逻辑分离。
- 建立可复用的 SVG sprite 或 icon 函数，不要在每个按钮散落不一致的图标代码。
- 输入、按钮、筛选、抽屉、提示和键盘焦点必须可用；不要以 `div` 冒充全部控件。
- 不要一次做很多浅页面。每个承诺的按钮都应可点击并产生业务反馈。
- 对规则来源不确定的交互，明确标为“原型假设”或“Phase 2 待确认”。

## 完成前检查

用 [references/prototype-acceptance.md](references/prototype-acceptance.md) 逐项验证，并实际运行原型检查关键交互。发现未通过项时直接修复；不要把明显缺陷留作“后续优化”。
