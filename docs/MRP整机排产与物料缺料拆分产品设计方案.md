## 1. 结论与边界

将现有一个混合工作台拆成两张责任明确的页面：**排产计划**负责整机日计划、整机日产能、调日、执行锁定；**物料缺料**负责多层 BOM 净需求、末级备料、共享库存分配、异常决策、风险和来源追溯。两页引用同一批次、同一输入版本组、同一 active run、同一正式发布版本；不能建立两套各自发布的计划。

推荐目标流程是“整机候选排产 → 排产员确认 → 物控展开与复核 → 物料异常回传排产员 → 必要时调整并重新复核 → 联合门禁发布 → 执行反馈”。正式发布仍是一个动作，整机确认只是内部交接，不等于已发布或已投产。

名称叫“物料缺料”，明细字段必须叫“末级需求物料”，不能一律叫“原材料”：有效 STOP 策略会让机头、PCBA 等成为需求终点。当前能够准确算的是**逐层净需求与库存风险**，还没有采购在途、采购单、承诺到货、替代料和提前期的供给覆盖数据，不能把末级净需求声称为“真实采购短缺量”或“到料缺口”。

## 3. 当前代码事实与不可跳过的差距

1. frontend/src/router/index.ts 的 /planning 和 /planning/:id 都进 MrpWorkspace；frontend/src/views/mrp/MrpWorkspace.vue 把整机、末级需求、库存分配、异常、执行和发布放在同一工作台。frontend/src/config/menu.ts 把全部相关权限前缀归入“排产计划”。

3. 已有自然可复用的数据事实：逐层 mrp_requirement_detail、末级 mrp_terminal_demand、日 mrp_daily_plan_detail；后者用 terminal_type 区分 MACHINE_OUTPUT 与 TERMINAL。已有 RequirementTrace、InventoryAllocation、DecisionCenter、StockRiskPanel、MaterialPolicyNoticePanel 等组件。
4. 当前创建、预检、计算、发布共用 mrp_calc_batch 和 active_run_id。预检先对整条 BOM 展开并生成角色、物料、库存等问题；若进入 WAITING_DECISION，就不能产生整机日结果。因此“只拆导航”不能满足“先独立排整机、后分析缺料”。见 BatchOrchestratorService.precheck、submitCalculation 与 MrpCalculationService、DailyPlanningService。
5. 整机跨日调整当前通过 LinkedDailyTransferService 在同一事务里搬移全部关联末级事实，还允许操作者改末级建议量；单一 mrp_plan:adjust 权限没有划开两个角色的写入责任。
6. 发布已检查待决策、待分配、物料策略默认确认、库存风险、日历、守恒及 checksum；新方案必须保留。已发布批次产生独立版本，修订生成新草稿；不能原地覆盖旧版本。
7. 现有 terminal-demands/page 与 requirements/page 的筛选能力不足以直接支撑独立缺料列表；必须在 SQL 层补工厂、来源月、整机、末级物料和异常状态过滤，维持服务端分页。

## 4. 两张页面的功能边界

### 4.1 排产计划（排产员负责）

- 路由保留 /planning 与 /planning/:batchId；默认只显示 MACHINE_OUTPUT。表格行是“工厂＋整机料号＋来源月”，列是冻结业务周下的日日期；日事实为唯一真源，周/月只读聚合。
- 保留生成候选排产、整机库存扣减后的净台数、日产能负荷与预警、生产日历、合法生产日跨日调整、已锁定/已执行、实际完成量、版本历史、修订和正式发布。
- 顶部只展示与该整机版本对应的物料状态摘要：“未分析／分析中／待物控处理／待复核／已确认／已过期”。点击风险数跳到缺料页并携带 batchId、工厂、整机和日期。
- 排产员不能在此直接改末级数量、共享库存分配或缺库存判定。整机调日预览可只读列出关联备料影响；提交仍由后端一次原子完成系统联动，随后使物料确认失效。
- 若缺料反馈要求改期/减量，排产员在本页查看受影响整机和建议，再决定调整；缺料页不能偷偷改整机最终排产。

### 4.2 物料缺料（物控/物料计划员负责）

- 新增顶层入口 /shortage 与 /shortage/:batchId，与排产页显示同一批次/activeRun/输入指纹。历史版本只读。
- 默认“按物料汇总”看工厂、仓库/库存池、物料编码/名称/单位、来源月/需求日、毛需求、良品可分配库存、安全库存、已分配、净需求、风险、处理人和状态；共享物料只能按同一库存池汇总一次。
- 下钻“受影响整机”显示每个来源整机、来源月、BOM 路径、根整机排产日期、逐层 gross/allocated/net、STOP/结构叶子原因和对应日备料。另提供“按整机查看”，从排产页跳入时使用相同过滤条件。
- 复用现有决策中心、库存分配、策略提示、风险及追溯；缺库存记录与零库存记录分开显示，良品与不良品分开显示，安全库存硬保底，预警库存只显示风险。
- 物控可维护已有业务决策、显式库存分配覆盖及末级备料调整；每次操作记录系统值/人工值/最终值、原因、操作者、时间与 revision。物控无整机数量或日期写权限。
- 物控复核后形成“本次物料分析已确认”，绑定 batchId、activeRunId、整机计划 revision/有效结果指纹及物料结果 checksum；之后整机调整、重算或输入失效会自动取消确认。物控可提交“需要改排产”的反馈项，不能仅在备注中口头协商。
- “缺料”标签下分开显示三类量：末级净需求（可计算）、库存预警/异常（可计算）、到料覆盖缺口（当前不可计算）。到料覆盖缺口区域在接入在途/采购/交期前明确标为“未纳入本期”，不显示虚假的零。

### 4.3 两页共享且只有一个版本详情

两页顶部统一展示 batchId、工厂范围、forecast 版本、每仓库库存版本、BOM 内容 checksum、分类角色/策略/日历/业务周版本、activeRunId、排产 revision、物料复核状态与正式发布时间。切页不复制业务事实；历史链接永远精确指向同一版本。历史 v4 及更早规则只读保留旧口径，不补造 MACHINE_OUTPUT。

## 6. 业务状态与闭环路径

状态建议保留 mrp_calc_batch 既有技术状态，新增两个业务维度，不把所有组合硬塞进一条大状态机：

- scheduleReview：未生成 → 待排产员确认 → 已确认 → 因整机改动待重确认。
- materialReview：未分析 → 分析中 → 待决策/待复核 → 已确认 → 因排产或输入变动已过期。
- batchPublish：现有草稿/计算/READY/已发布/历史；正式发布门禁读取两个 review 维度及现有校验。

主要闭环如下：

1. 经营计划、厂仓映射、良品库存、安全/预警库存、生产日历、业务周和 BOM 当前同步校验码组成候选批次输入。
2. 系统对整机层先扣本厂冻结良品库存，形成整机月净台数和 v5 日排产；排产员处理整机产能预警并确认候选日计划。整机层缺库存记录仍需明确确认，不能悄悄按零。
3. 物控基于该候选批次的整机净需求展开多层 BOM，遵守每层扣库、STOP/EXPLODE、共享库存确定性顺序及现有 6 位精度；在缺料页处理异常、风险、备料日计划并确认。
4. 物料不可满足时，物控提交关联整机、工厂、来源月/计划日期、影响数量、原因、建议日期与责任人。排产员调整或记录明确的风险接受决定；调整后物料确认自动失效、重新分析。页面展示差异，而不是默默覆盖历史判断。
5. 两岗都确认且全部现有发布门禁通过后，发布责任人发布同一版本；生产执行/锁定与后续库存实际变化触发新修订或新批次，不回写已发布历史。

这里有两种闭环层级：本期可以做到**计划/库存净需求闭环**，包括角色确认、调整、再分析及发布；若要证明“某日真实不缺料”，还必须接入采购在途、预计/实际收货、供应商承诺及时间相位覆盖，并在下一范围设计供给单及回写。当前版本不得将前一种结果冒充后一种结果。

## 7. 计算、版本和失效规则

- 保持单个 batchId、统一工厂范围和 activeRunId。新批次仍直接使用 BOM 管理当前同步关系及 checksum；BOM 重新同步后按 C023 重建批次。库存仍按仓库冻结版本和良品优先级使用；跨工厂不混用。
- 整机月数量来源仍是经营计划根行，先扣整机库存。现有 v5 业务周“按来源月实际周数均分、整体提前一业务周、周余数归首份”不改；整机为整数台，末级用 BigDecimal/DECIMAL(18,6)。旧规则历史回放保持原样。
- 若采用完整两阶段计算，物料阶段必须使用**同一已确认整机净需求和排产 revision**，不能重新按整机原始 forecast 扣一次根库存。把“根库存净算”抽为共享步骤，物料引擎从已净额根需求进入子层；root STOP 等边界需保留原结果。
- 当前末级月净需求与整机日计划由同一计算生成，且备料日分布有独立 v5 均分。若先确认了人工调整的整机日程再运行物料阶段，必须确定性重放整机调日事件到备料日事实，或设计等价且守恒的派生算法；不能简单用整机日期覆盖全部子件日期。重放失败时保留旧 active run 并给冲突项，禁止 READY 半版本。
- 每次整机调日保留现有“整机＋全部关联末级”原子事务和两端守恒；排产员请求只提交整机量，由服务端采用现有比例建议值形成备料联动。物控需要的人工备料偏差在缺料页单独留原因和审计。若某行小数残余不能整数搬移，继续保留残余和异常，不凑数。
- 物料确认至少绑定 batchId＋activeRunId＋scheduleRevision＋resultChecksum；这几个值一变即失效。当前批次计算输入变更按现有 STALE 规则阻断发布；已锁定/已执行日不可重排，已发布版必须创建修订。
- 新确认字段建议存业务确认记录表（确认类型、上述指纹、状态、操作者、时间、原因），而不是覆盖自动计算值。新审计事件记录确认、撤销、风险接受和改期反馈。

由于阶段 17 Prompt 曾规定“单一顶层入口”，两份现有原型也把整机和末级放在同一页，实施前须把这次用户需求写成新裁决、更新需求/契约和可交互原型，再修改路由与代码。已应用 Flyway 文件不可变；不得引入新中间件。

## 9. 分批交付与真实成本

**A. 快速分工版（较小改动）**：新增缺料入口、整机专用网格、物控复用组件、权限和物料确认；继续一次联合预检/计算/发布。这能立刻解决“页面和角色混在一起”，但 BOM/库存异常仍会阻断整机结果生成，不能宣称已实现严格的先排整机后算缺料。

**B. 目标闭环版（推荐纳入同一产品变更的后续实现）**：再分出根整机预检/排产，整机确认后才展开物料；完成调日事件重放、失效指纹、物控反馈与联合发布。这样才满足两岗按顺序交接且整机可先成稿。算法公式、历史回放、仓库优先级和版本主体保持不变，但状态协调和验证工作不可省略。

**C. 供给覆盖版（另行立项）**：接入在途、采购/委外订单、预计及实际收货、提前期、替代料与供应动作，增加分时净可用和可采购短缺量；这是从“库存净需求”升级到“真实到料缺口”，不应混入 A/B 的验收口径。

建议先把 A 做成可评审、可切换的页面与权限，再完成 B 后宣布“业务拆分闭环”。A 若独立上线，必须在产品说明中明示其预检耦合限制。

## 10. 关键验收案例

1. 一个整机 A 来源月净 100 台，可先在排产页看到 100 台按 v5 分日；没有原料库存记录时，排产页面能给候选计划，缺料页显示待确认记录，最终发布仍阻断。仅 A 快速分工版会在此失败，应作为 B 的阶段门禁。
2. 整机 A、B 共享物料 X，同厂同仓良品库存只分配一次；安全库存保底、不良品不参与、不同工厂不串用，顺序按来源月和经营计划优先级。
3. A 的 STOP 机头和 B 的原料都在缺料页出现，列名均是“末级需求物料”；从物料下钻可回到正确整机、来源月和 BOM 路径。
4. 排产员把 A 的某日 17 台搬到另一生产日，全部关联末级在一个事务里按现有整数建议联动，整机/物料总量守恒；物料确认变为“待复核”，旧指纹提交返回 409。
5. 物控提出“X 无法按期备料”，排产员调整后物控重新分析；未复核时发布失败，确认后同一版本才发布，旧发布版保持可查。
6. BOM 同步变化、库存版本变化、生产日历变化、人工共享库存分配改变、修订和月中锁定分别验证失效/重建规则；已执行日不能被覆盖。
7. 末级净需求、库存风险、缺库存记录三类字段不混淆；在途未接入时“到料缺口”显示未计算，绝不显示 0。
8. 两页角色 401/403、跨工厂越权、空数据、失败任务、分页筛选、大范围 84 日滚动、整机/物料导出均通过真实 API 与浏览器验证。
