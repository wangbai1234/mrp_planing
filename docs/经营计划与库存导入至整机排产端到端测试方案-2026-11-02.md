# 经营计划与库存导入至整机排产：端到端测试方案

版本：2026-11-02；状态：**执行中，整体验收未通过**。实际执行结果和逐项状态见 [执行记录](经营计划与库存导入至整机排产端到端执行记录-2026-11-02.md)。本文件保留原始验收口径，不将已测子项等同于整条场景通过。

## 1. 目标、范围和现行链路

本轮验证从经营计划 Excel 与库存 Excel 上传、预览、确认，到创建排产批次、预检、异步生成整机日计划、排产员复核及物控接收条件的完整链路。排产页面的日、周、月、负荷、调整、历史、版本信息和错误状态都纳入。物料缺料仅验证**交接边界**：整机未确认时不可开始，确认后可开始，整机调整后确认失效；物料逐层展开和正式发布另按缺料专项 UAT 验收。

代码已核对的实际数据流：

1. `ForecastImport.vue` → `POST /api/v1/forecast-imports` → `ForecastExcelParser` → 上传任务暂存；无错误后 `POST /forecast-imports/{taskId}/confirm` → `ForecastImportService` → `forecast_version`/`forecast_detail`。确认后当前经营计划版本推进，先前使用旧版本的进行中批次可能转为 `STALE`。
2. `InventoryImport.vue` → `POST /api/v1/inventory-imports/items` → `InventoryItemExcelParser` + 仓库主数据校验；确认接口 `/inventory-imports/items/{taskId}/confirm` 生成 `inventory_snapshot` 和 `inventory_item`。现行页面走 `items` 路径；旧 `/inventory-imports` 是兼容接口，不能用其成功代替现行页面验收。
3. `BatchCreateDialog.vue` 从已导入经营计划、**一份统一导入**的库存版本、当前同步 BOM、已发布分类角色、工厂仓库映射、生产日历和业务周取数；`MrpBatchController.createBatch` 冻结输入、建 `DRAFT`。已有未完成批次时服务端返回冲突。
4. 排产页新建后自动调用 `precheck`；日历/业务周缺项会停止预检。通过后 `READY_TO_CALCULATE`，页面提交异步计算，成功形成 `SCHEDULE_READY` 整机候选日计划；`schedule-confirmation` 写与当前日计划指纹绑定的确认记录。**确认不要求把批次状态改成其他值**，页面应根据复核记录显示“整机已确认”。
5. 缺料页依据同一批次的有效整机日事实及复核指纹判断能否开始物料分析。两岗位不依赖互跳按钮。批次、任务、run、输入版本和结果校验码必须能串联追溯。

主要依据：`project.md`、`.harness/import-contract.md`、`.harness/test-and-gates.md`、`.harness/source-precedence.md` 的 C014/C016/C019/C022/C023/C024/C025，以及后续 `docs/MRP排产与缺料分岗页面裁决-2026-11-02.md`（C026）。旧 `test-kit/2026-10-15` 的输入可借用，**旧 v4 三份拆周预期和旧跨页 E2E 断言不可直接作为当前 v5/C026 预期**。

## 2. 运行隔离与执行前门禁

- **先只读核对**代码版本、`git status`、当前 API/Worker/前端进程、端口和前端代理目标；不得重置脏工作区、清共享 Redis 或删除数据库卷。Node 24、Java 21 不匹配时按 `AGENTS.md` 的环境规则暂停，不安装或改项目版本配置。
- 浏览器入口固定 `http://localhost:5180`。破坏性导入与批次测试必须使用独立 MySQL 8 数据库、Redis、API/Worker 和上传目录；建议隔离端口 MySQL `3317`、Redis `6391`、API `8180`。启动 5180 前以 `MRP_VITE_API_TARGET=http://127.0.0.1:8180` 配置代理，并用浏览器 Network 与真实 API 身份验证其确实连接隔离环境。若 5180 已由连接主库的前端占用，**禁止直接在其上执行写入测试**；先安全复用或调整隔离前端映射，并记录实际入口。
- 复用已经存在的 `test-kit/2026-10-15` 隔离现场，先核对 PID、容器和卷，再增量导入。测试开始与结束都记录被保护主数据/BOM 表的行数和校验和；不通过修改真实物料、BOM、分类或源库来绕过失败。旧测试包的 `BUG-01/02` 证据是 2026-10-15 的历史记录：现行 `V045` 已有工厂维度唯一键，是否仍复现必须以本轮实际结果判定。
- 执行前只读检查：所选工厂、启用仓库及良品属性、仓库优先级、业务周、日历覆盖、分类角色版本、库存控制策略、当前同步 BOM 及已有未完成批次。只使用有效料号制作输入；异常料号场景只做到**导入拒绝**，不写主数据。每份测试 Excel 使用唯一文件名并保留 SHA-256；重复文件/重复确认用例则明确复用同一字节。
- 新批次只能有一个未完成当前批次：按表中顺序完成/正式取消上一批次后才创建下一批次，不允许直接改数据库状态。黄金批次先采集未调整的事实和 checksum，再做调日；历史和失败现场保留。

## 6. 执行顺序与可量化门禁

1. **环境与数据保护**：记录版本、端口、代理、库、Worker、工厂权限、主数据保护校验；先做编译和现有相关自动测试，不把旧脚本的弱断言当通过。旧 `frontend/e2e/business-flow.spec.ts` 写死 5183/8080 且大量条件跳过；旧 `phase2-mrp.spec.ts` 仍断言两页互跳。应新增/更新当前 E2E 脚本，以真实登录、隔离库和强断言执行。
2. **导入异常优先**：F02–F10、I02–I08 先测负例，断言失败不改变版本/快照；若发现 P0/P1 缺陷，保留文件、响应、日志和数据库前后值，按仓库 bug 流程修复并重测。
3. **最短成功链**：D0 的 F01→I01→B01→B03→B05→B10→B13→B14。每一步记录 `taskId/versionId/snapshotId/batchId/runId` 和 UI 截图；失败不跳到后续场景。
4. **多工厂/多库存/时间/多批次**：D1、D2、D3、D5 分批顺序运行。对整机结果使用独立 `Decimal` 预期，按每个工厂、整机、来源月、实际日逐键比对；另核对全局负荷以及周/月汇总，不仅比较总行数。
5. **前端与权限**：用排产员、物控、只读、工厂受限账号分别打开页面和直接调用 API；页面截图与 Network/Console 一并保存。
6. **稳定性与容量**：先小后大；1 万物理行需要完整 Excel 上传、确认、版本行数对账；十万行若尚无 XLSX 或触发生成器 OOM，标 `BLOCKED/NOT_RUN`，不得把 CSV 或预计性能写为 PASS。记录解析/确认/预检/计算耗时、峰值内存、SQL 与响应大小；阈值以真实基线和业务 SLA 冻结，不预编造。
7. **回归与结论**：任何代码修复必须依次后端 `./mvnw compile`、`./mvnw test`，前端 `npm run build`、`npm test`、类型检查，再以隔离 API/Worker/5180 浏览器、Playwright 真正复测；保存结果，独立复核后才标通过。纯测试方案文档的创建不等于运行了这些门禁。

阶段门禁：P0 全过、P1 无未关闭缺陷；每个正式导入无部分落库；来源月根量与日事实、日周月以及整厂负荷全部对账；整机确认和跨岗门禁准确；源库保护校验无变化。任一项不满足，整体标 `FAIL/BLOCKED`，不可声称“完整通过”。

## 7. 证据与缺陷记录格式

每条用例使用 `PASS / FAIL / BLOCKED / NOT_RUN`，记录：执行时间、隔离环境标识、Git revision、输入文件 SHA-256、账号角色/工厂域、请求路径及状态码、版本/快照/批次/任务/run ID、预期/实际、数据库只读对账、截图/trace/日志路径、缺陷号、复测结果。性能数据写真实耗时和样本规模，不以页面“加载完成”替代数量验证。trace 与响应可能含 JWT、料号或业务数据，仅保留私有证据目录，分享前脱敏。

失败处理：先确定是输入数据、配置、权限、接口、Worker、SQL 或页面呈现哪层错误；保留原始失败文件和现场；建立缺陷单并注明最小复现；修复后跑失败用例→相邻回归→三层验证。不要删除失败数据、修改旧 Flyway、用数据库直改状态或降低断言。
